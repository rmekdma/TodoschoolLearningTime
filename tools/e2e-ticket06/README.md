# Ticket 06: task removal and reboot recovery

This scenario uses the Ticket 02 prepared tablet and the existing local fake API fixture. It runs the observer against the already-installed debug APK; it does not install or rebuild the product APK.

Run `Run-Ticket06.ps1 -RefreshObserver` after building the observer. Run `Run-Ticket06.ps1 -RunPrepared -Case task-removal` and `Run-Ticket06.ps1 -RunPrepared -Case reboot-recovery` as separate cases. The prepared manifest, observer signature, connected device, notification/accessibility settings, and local-only API URL are checked before each case starts. The reboot case configures the synthetic account through the actual debug UI, saves the target counts and one-minute interval, captures their exact app preference rows on the PC, then acknowledges that capture before the single reboot. Its evidence explicitly records that task removal was not part of that case.

The task-removal case observes the real debug task in Recents, records a host-captured screenshot and SHA-256, and registers its exact task ID/component plus the IDs of all other recent tasks. Accessibility label observation is optional: if Android does not expose it, the gate records `false` and null label/window fields so the screenshot can be inspected by the parent and user. The observer performs no task-removal command or gesture. The host writes `task-removal-human-gate.json`; after the user identifies and dismisses only that exact card, the parent records the provided acknowledgement body at its loopback endpoint. The case passes only when the matching acknowledgement and an observed missing target task are both present and all other task IDs remain unchanged. A 30-minute gate timeout is a failure. The observer then opens the real Hangeul app and verifies the exact five-request foreground cycle and live service lease. The separate reboot case verifies persisted registration, target counts, and an explicitly saved common interval, then observes the boot-restored service before any product Activity is opened. Its first silent recovery baseline requires all seven requests (sign-in, three catalogs, and three reports). The later real Todo foreground completion requires the five-request subject cycle (sign-in, three catalogs, and only that subject's report). If the boot baseline does not complete, the observer can bring the real Todo subject app to the foreground to trigger the service's next eligible cycle; it records that trigger separately from an automatic baseline.

All server traffic stays on `127.0.0.1` over the configured ADB reverse. Fixture credentials and data are synthetic. The saved run directory under `build/e2e-ticket06/` contains bounded observer results, filtered preference and device evidence, fixture snapshots, APK hashes, and source provenance. A successful reboot-only run writes `ticket06-reboot-recovery-evidence.json`; it does not claim the separate task-removal case passed. The device in this prepared scenario is API 33; it does not provide Android 15/API 35 coverage. Notification assertions cover the existing low-importance silent channel and notification-manager update result; they do not claim audible or heads-up behavior.
